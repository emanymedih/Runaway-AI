# Проверка стороннего скилла

## Статический аудит

| Риск | Где искать |
| --- | --- |
| Код при установке | install scripts, postinstall, shell, package.json, pyproject.toml |
| Неожиданные команды | hooks, background tasks, расписание, автообновление |
| Сетевая передача | URL, endpoints, telemetry, вебхуки, curl/wget |
| Секреты и файлы | .env, SSH, личная почта, home, tokens |
| Зависимости | новые пакеты, pinned versions, скачивание бинарников |
| Откат | процедура удаления, отзыв сервисных разрешений, восстановление файлов |

Анализируй статически, без исполнения. Низкая видимая опасность ещё не означает гарантированную безопасность.

## Оценка ценности

- Кто автор и какова проверяемая методика.
- Какой шаг скилла не приходит модели самостоятельно в обычной задаче.
- Что содержат реальные тесты, какие задачи, сколько повторов и какая цена.
- Есть ли активное обсуждение ошибок и обновлений.
- Не перегружен ли SKILL.md правилами, которые портят качество.
- Требует ли скилл слишком широких доступов относительно пользы.

## Честное сравнение

Для 2–3 одинаковых сценариев сопоставляй: базовая модель, модель с кратким промптом, модель со скиллом. Сохраняй одинаковыми исходные данные и критерии. Оцени полноту, точность, пригодность результата, время, стоимость, вмешательства пользователя, риск. Если реального исполнения не было, записывай «план теста», а не «тест пройден».

## Заметные семейства методов

- Дизайн: выбор стилистического направления и проверка доступности.
- Разработка: требование, план, изоляция изменений, тесты и проверяемость.
- Исследования: сначала извлечь результаты, затем оценить выводы.
- Планы: premortem и сигналы провала.
- Обучение: журнал прогресса, контрольные вопросы и воспроизведение по памяти.
- Редактура: разбор конкретных правок с авторским выбором.

Эти примеры взяты из статьи; их применимость к текущим версиям скиллов нужно перепроверять.
